# M2 — technical functionality

**Status:** done  
**What this milestone is:** take a job description, score the warehouse against it, always print a pick list. No LLM, no embeddings, no paid APIs. Weak coverage still ships (`3/9` is a number, not a stop).

M1 docs (`M1.md`, warehouse manual) are unchanged. This file is M2 only: every function on the apply path, in the order it actually runs.

---

## 1. What M2 does, and what it does not

M2 answers one question: **given `~/.resume/profile.yaml` and a JD, which jobs / projects / bullets should this resume keep?**

| Does | Does not |
|---|---|
| Fetch a public JD URL, read a file, or accept a paste | Board-specific APIs (Indeed login, Greenhouse tokens — that's M5) |
| Split the JD into must / nice / body / ignore | Invent skills the warehouse never mentioned |
| Find tech terms from a built-in lexicon **plus** warehouse vocab | Run Ollama, OpenAI, or embeddings |
| Score every warehouse item against those terms | Rewrite bullets or generate filler |
| Pick top 3 jobs, top 3 projects, 4 bullets each | Export a PDF (M3) |
| Report `missing` must-haves and pick-list `coverage` | Block on low coverage |
| Treat “Tableau, Power BI, or similar” as one requirement | Treat unknown JD words (e.g. a vendor name not in the lexicon or warehouse) as skills |

Truth is still user-authored text. Matching is word-boundary / span-masked regex against a finite term list.

---

## 2. How you invoke it

Needs a warehouse first (`resume init` from M1). Two entry points share the same matcher.

### `resume new`

```bash
resume new https://example.com/job
resume new ./jd.txt
resume new -                         # paste, empty line to finish
```

Loads the profile, runs `JobMatcher`, prints the plan, then the M3 teaser (`after_plan`).

### `resume init` session

After first import (or if a warehouse already exists), `init` drops into a loop:

| Choice | What happens |
|---|---|
| `paste` (default) | First line is a URL / existing file path → match that source. Anything else → keep reading until a blank line, then match as paste. |
| `update` | Merge another PDF, or type a job / project / bullet (M1 warehouse writes). |
| `show` | Print the warehouse. |
| `quit` | Exit. |

`_match_job` is the shared function. `resume new` is the power-user shortcut; `init` paste is the product shell.

## 3. Pipeline

```
source (URL | file | '-')
    │
    ▼
JobSourceRouter.resolve
    │   URL  → GenericFetcher (httpx + BeautifulSoup)
    │   file → utf-8 text
    │   '-'  → pasted string
    ▼
JobPosting { url, source, title?, raw_text }
    │
    ▼
JobAnalyzer.analyze(posting, profile)
    │   1. JobDescriptionCleaner  → posting.clean_text
    │   2. profile_vocabulary     → skills ∪ vocabulary
    │   3. KeywordMatcher.extract → must, nice, keywords, alternatives
    │   4. inventory_keys         → every term the warehouse can back up
    │   5. missing                → must-haves with no inventory hit
    ▼
JobAnalysis { must_have, nice_to_have, keywords, missing, alternatives }
    │
    ▼
ResumePlanner.plan(analysis, profile)
    │   BulletScorer weights each term
    │   rank bullets, pick top-N items
    │   coverage over selected picks only
    ▼
ResumePlan { selected, excluded, scores, must_have_hit, must_have_total }
    │
    ▼
cli_ui.print_plan
```

Facade: `JobMatcher.run(source, profile, pasted=)` in `app/apply.py`. Three objects, no I/O beyond the fetch.

```
JobMatcher
  ├─ JobSourceRouter
  ├─ JobAnalyzer
  │    ├─ JobDescriptionCleaner
  │    └─ KeywordMatcher  → TermIndex
  └─ ResumePlanner
       └─ BulletScorer    → TermIndex
```

## 4. Models (`app/models.py`, M2 block only)

Warehouse types from M1 (`Profile`, `Item`, `Bullet`, …) are unchanged. M2 adds four dataclasses.

### `JobPosting`

| Field | Meaning |
|---|---|
| `url` | Fetched URL, or file path as string. Empty for paste. |
| `source` | `"url"` / `"file"` / `"paste"` |
| `company` | Unused today (always `None`). Reserved for M5 boards. |
| `title` | First `h1`/`h2`, else `<title>`. `None` for file/paste. |
| `raw_text` | Visible page text or file/paste body. |
| `clean_text` | Filled in by the analyzer after chrome is stripped. |

### `JobAnalysis`

| Field | Meaning |
|---|---|
| `must_have` | Display names found under Requirements-style headings (or the whole body if no such heading). |
| `nice_to_have` | Display names under Preferred / Nice to have, plus must-section lines with “a plus” cues. Never also in must. |
| `keywords` | Deduped `must + nice + body` (Responsibilities / About the role / Our stack). |
| `missing` | Must-haves the **warehouse** cannot back up (inventory check, not pick-list coverage). |
| `alternatives` | Groups of display names that are either/or on the same line. |

### `PlannedPick`

| Field | Meaning |
|---|---|
| `item_id` | `exp.N` or `proj.N` |
| `bullet_ids` | Up to 4, highest bullet score first (stable order on ties). |
| `reason` | `"matches: PostgreSQL, SQL, …"` or `"best available overlap"` if zero term hits. |
| `score` | Item score from `BulletScorer.score_item`. |

### `ResumePlan`

| Field | Meaning |
|---|---|
| `selected` | Experiences then projects, each already truncated to budget. |
| `excluded` | Every other item id (education is never selected). |
| `scores` | `{item_id: float}` for **all** scored items, not just selected. |
| `must_have_hit` / `must_have_total` | Coverage over **selected** picks. Either/or groups count as one unit. |
| `coverage` | Property: `"hit/total"` string for the CLI. |

## 5. Fetch — `app/fetching/`

### `JobSourceRouter.resolve(source, pasted=)`

| Input | Result |
|---|---|
| `"-"` or `"paste"` | `JobPosting(url="", source="paste", raw_text=pasted)`. Empty paste → `ValueError`. |
| `http://` or `https://` | Lazy-import `GenericFetcher().fetch(url)`. |
| Existing file (via `ResumePathResolver`) | Read as UTF-8 (`errors="replace"`). `source="file"`, `url` = path. |
| Anything else | `ValueError` with a usage hint. |

No content-type sniffing. A `.pdf` path is treated as text and will be garbage; paste or a `.txt`/`.md` is the intended file path.

### `GenericFetcher.fetch(url)`

1. `httpx.get` with a Chrome User-Agent, `follow_redirects=True`, 20s timeout.
2. HTTP errors become `FetchError` (`Could not fetch {url}: …`). The CLI prints that and suggests pasting.
3. BeautifulSoup `html.parser`. Decompose `script`, `style`, `nav`, `header`, `footer`, `noscript`, `svg`.
4. Title = first `h1`/`h2` text, else `<title>`.
5. `raw_text` = `soup.get_text("\n", strip=True)`.

JS-only job pages (LinkedIn, many ATS shells) come back thin. Paste with `resume new -` or the init loop.

No cookies, no login, no Playwright. That is intentional for M2.

## 6. Clean — `app/analyzing/cleaner.py`

`JobDescriptionCleaner.clean(raw_text)` is line-oriented, no LLM.

1. Collapse runs of spaces/tabs on each line.
2. Drop empty lines.
3. Drop a line if it **starts** (case-insensitive) with: cookie, subscribe, sign in, log in, apply now, skip to, privacy policy, terms of service, all rights reserved.

It does **not** drop Benefits / EEO / salary. Those are section-classified later and ignored for term extraction.

## 7. Terms — `app/analyzing/terms.py`

This is the shared vocabulary for analyze, score, and (later) import. Everything compares as **canonical keys**, not raw strings.

`Postgres`, `PostgreSQL`, `postgres` → key `"postgresql"`, display `"PostgreSQL"` (or the user's warehouse spelling if they have one).

### `LEXICON`

A dict of **display name → alias list**. Covers languages, frontend, backend, data/ML, databases, cloud/infra, and named practices JDs ask for (`data pipelines`, `A/B testing`, …).

The lexicon includes skills the user may **not** have (Kubernetes, C#, Kafka, …) so they can appear in `must_have` and then in `missing`. Matching is not limited to warehouse skills.

Examples of aliases:

| Canonical | Also matches |
|---|---|
| JavaScript | js, ecmascript, es6 |
| Go | golang |
| C++ | cpp, c++11 … c++23 |
| scikit-learn | sklearn, scikit learn |
| PostgreSQL | postgres |
| Kubernetes | k8s |
| REST | rest api, rest apis, restful |
| machine learning | ml (only via the case-sensitive pattern) |
| Power BI | powerbi |
| AWS | amazon web services |

Add new tech here. Extra CLI aliases can also be passed into `TermIndex(..., aliases=)` but the matcher currently uses the default lexicon only.

### `IMPLIES` (one hop)

Having the left key counts as evidence of the right keys **on the warehouse side only**. Never used to decide what the JD asked for.

| Having | Also counts as |
|---|---|
| postgresql / mysql / sqlite / sql server / snowflake / bigquery | sql |
| supabase | postgresql, sql |
| pytorch / tensorflow / keras | machine learning, deep learning |
| scikit-learn | machine learning |
| fastapi / flask | python, apis |
| django / pandas / numpy | python (pandas also data analysis) |
| typescript / react / next.js / react native / node.js | javascript (and react where listed) |
| dax | power bi |
| power bi / tableau / looker | dashboards, data visualization |
| s3 / ecs / ecr / ec2 / lambda | aws |
| git | version control |
| graphql / rest | apis |

`TermIndex.expand(keys)` adds implied keys once. No recursion (PostgreSQL → SQL, not further).

### `TermIndex`

Built from lexicon + `profile.vocabulary` + `profile.skills`.

**User terms.** `add_user_term` splits `"HTML/CSS"` on `/` into HTML and CSS, except the literal `CI/CD`. Unknown user words become their own keys (so a warehouse skill like `Looker Studio` is searchable even if it is not in the lexicon). Display prefers the user's spelling when they registered a single unsplit term; otherwise the lexicon name wins.

**Compile.** One regex per alias, **longest first**. Matching uses span masking: a claimed span is overwritten with spaces so a shorter term cannot fire inside it.

- `C++20` is claimed before `C++` before `C`
- `React Native` before `React`
- `Node.js` before `js` (so it never also counts as JavaScript via the `js` alias)

Boundaries are `(?<![\w+#])` … `(?![\w+#])` so `C++` is not a prefix of a larger identifier and `#`/`+` stay attached to `C#` / `C++`.

**Case-sensitive / ambiguous names** (`_CASE_SENSITIVE`):

| Key | Pattern intent |
|---|---|
| go | `Go` only, not `go to` |
| c | `C` not followed by `-` or `&` (`C-suite`, `C&I`) |
| r | `R` same (`R&D`) |
| rest | `REST` only |
| ml | only via the machine-learning pattern, not the word “ml” in other words |
| node | not as a free English word; `node.js` / `Node` handled by the Node pattern |
| swift, spring, express, dart, julia, oracle, lambda | exact product casing |

`find(text)` → unique canonical keys in first-appearance order.  
`find_spans(text)` → `(start, end, key)` used for either/or grouping.

`key(term)` / `display(key)` are the only way analyze and score talk to each other. The scorer never compares `"Postgres"` to `"PostgreSQL"` as strings.

## 8. Keywords — `app/analyzing/keywords.py`

`KeywordMatcher.extract(clean_text, vocabulary)` returns

```
(must_have, nice_to_have, keywords, alternatives)
```

all as **display names**.

### Section split

The cleaner output is walked line by line. Current bucket starts as `"body"`. A heading line switches the bucket.

| Bucket | Heading examples |
|---|---|
| **must** | Requirements, Qualifications, What you'll need, Who you are, About you, Must-haves, Skills required, What you bring, … |
| **nice** | Nice to have, Preferred, Bonus, Pluses, Desired, Extra credit, Exposure to, “that would set you apart” |
| **body** | Responsibilities, What you'll do, About the role/team/job, The opportunity, Day-to-day, Our stack, Tech stack, Overview, Job description |
| **ignore** | Benefits, Perks, Compensation, Salary, Pay, About `<company>` (but not About you / About the role), Who we are, EEO, Diversity, How to apply, Why join |

**Heading detection** (`_heading`):

- Strip leading/trailing `*_#` emphasis.
- A line is a heading if it matches a section regex **and** either:
  - it is short (≤ 8 words) and not a sentence (doesn't end in `. , ;`), or
  - it has inline content after `:` / dash (`Requirements: 3+ years…`).
- Prefixed titles work: `Your Moneris Career - What you bring` uses the part after ` - `.

Inline rest after a heading is classified in that section (so `Requirements: Python, SQL` counts).

**Per-line overrides, after the heading is applied:**

- Degree lines (`bachelor`, `master`, `degree`, `diploma`, `ph.d`, `post-secondary`) are skipped entirely. “Bachelor's in Statistics, Computer Science…” does not add Statistics as a skill.
- A line already in **must** that contains a nice cue (`preferred`, `a plus`, `bonus`, `ideally`, `an asset`, `set you apart`, …) is moved to **nice**.

### Fallback: no Requirements heading

If the must bucket is empty after the walk, every **body** hit that is not already nice becomes must. A JD that is just a blob of text still produces must-haves.

Benefits / About-us / EEO never contribute terms, even in this fallback.

### Term collection

```
must  = terms in must bucket
nice  = terms in nice bucket, minus must
body  = terms in body bucket
if must is empty: must = body − nice
keywords = unique(must + nice + body)
```

“Our stack: Redux” is body, not a requirement, unless there is no must heading at all.

### Either/or groups

On each must/nice line, `find_spans` walks term spans. A **run** of 2+ terms is an alternative group if:

- gaps between them are only whitespace, commas, slashes, and `and` / `or` / `and/or`, **and**
- at least one of: an `or` in a gap, the line continues with `or similar|equivalent|comparable|other`, or the run is introduced by `e.g.`

Examples that become one group:

- `Tableau, Power BI, or similar`
- `TensorFlow, PyTorch, or Scikit-learn`
- `(e.g., PostgreSQL, MySQL)`

Having **any** member satisfies the requirement (see analyzer + coverage).

## 9. Analyze — `app/analyzing/analyzer.py`

```
clean_text = cleaner.clean(raw)
vocabulary = unique(profile.vocabulary + profile.skills)
must, nice, keywords, groups = matcher.extract(clean_text, vocabulary)
inventory = inventory_keys(profile, TermIndex(vocabulary))
missing = [term in must if requirement_keys(term, groups) ∩ inventory is empty]
```

### Warehouse inventory

`inventory_keys` is every canonical term the warehouse can defend, then `expand`ed with `IMPLIES`:

- `profile.skills` and `profile.vocabulary`
- `index.find` on those strings (so `HTML/CSS` contributes both)
- every item's `tech` tags
- `index.find(item.title)`
- `index.find(bullet.text)` for every bullet

A must-have is **not** missing if it appears in a bullet even when it is absent from the Skills list.

`requirement_keys(term, groups)` is `{term}` plus every other member of any alternative group that contains it. If the JD says “Tableau or Power BI” and the warehouse has Power BI, Tableau is not missing.

**Missing vs coverage.** Missing is “does the warehouse contain this at all?” Coverage is “did the **selected** picks mention it?” You can have no missing skills and still show `2/7` if the planner did not pick the items that hold those skills.

## 10. Score — `app/planning/scorer.py`

`BulletScorer(index, analysis)` builds a weight table from analysis terms (later keys overwrite earlier):

| Source | Weight |
|---|---|
| `keywords` (body leftovers) | **1** |
| `nice_to_have` | **2** |
| `must_have` | **3** |

A term that is both body and must is stored as 3.

### Bullet score

Terms are taken from **`bullet.text`**, not `bullet.tech`. Older imports with bad tags still score correctly.

```
relevant keys = find(text) ∪ implied(those), intersected with the JD weight table
score         = sum(weight[k] for k in unique relevant keys)
```

A bullet that says “Built dashboards in PostgreSQL” against a JD that asks for SQL + dashboards gets PostgreSQL (→ SQL via IMPLIES) + dashboards, if those keys are in the JD.

### Item score

```
item keys = find(title) + key(each tech tag) + find(each chosen bullet)
          then imply + keep JD-relevant
unique    = sum of weights of those keys (once)
evidence  = +0.5 per chosen bullet that has any relevant term
score     = unique + evidence
```

`EVIDENCE_BONUS` (0.5) breaks ties toward items with more on-topic bullets without rewarding raw bullet count (only chosen bullets, max 4, and only if they hit).

`display(key)` uses the user's warehouse spelling when present.

## 11. Plan — `app/planning/planner.py`

Default budget (constructor-overridable, CLI uses the default):

| Slot | Count |
|---|---|
| experiences | 3 |
| projects | 3 |
| bullets per item | 4 |

Education is never picked.

### Per kind (`_pick`)

For each item of that kind:

1. Sort bullets by `score_bullet` descending. `sorted` is stable, so equal scores keep warehouse order.
2. Take the first 4.
3. `score_item` on those 4.
4. Reason string from the item's relevant display names.

Then sort items by score descending and keep the top 3. Zero-score items can still be selected if there are fewer than 3 better ones (**weak match still ships**; the reason becomes `best available overlap`).

`excluded` = every experience/project id not in `selected`. Scores dict includes **all** items of both kinds, so you can see why something sat on the bench.

### Coverage (`_coverage`)

1. If there are no must-haves → `0/0`.
2. Union `item_terms` of every **selected** pick (chosen bullets only).
3. Collapse must-haves into unique `requirement_keys` sets (either/or = one unit).
4. `hit` = how many of those units intersect the selected-term set.
5. `total` = number of unique units.

Coverage never raises, never blocks, never changes the pick list.

## 13. Worked example (thin SWE warehouse, DS-ish JD)

JD must-haves after section parse: `Python, SQL, Tableau, Power BI, dashboards`.

Warehouse: SWE jobs (Python, Docker) + one analytics internship (SQL, Power BI, dashboards). No Tableau skill listed.

1. **Terms.** Lexicon finds Tableau even though the warehouse never said it.
2. **Alternatives.** “Tableau, Power BI, or similar” → one group. Inventory has Power BI → Tableau is **not** missing.
3. **IMPLIES.** A “PostgreSQL” bullet also counts as SQL for inventory and scoring.
4. **Scores.** Internship bullets that mention SQL / Power BI get 3 each; Docker-only SWE bullets get 0 unless Docker is a keyword.
5. **Plan.** Internship ranks first. Two SWE jobs still fill the 3-job budget with `best available overlap` if nothing else hits.
6. **Coverage.** Selected internship covers SQL + Power BI + dashboards. Tableau is satisfied via the group. If Python only lives on a bench item, coverage is `4/5`, not a gate.

## 17. Invariants (product rules encoded in code)

1. **No LLM on this path.** Term lists and scores are deterministic.
2. **Unknown JD words are ignored** unless they are in the lexicon or the warehouse.
3. **Warehouse text is the only evidence.** Scores read bullet text / titles / tech / skills, never generated copy.
4. **Coverage is not a gate.** `ResumePlanner` always returns a pick list.
5. **Missing ≠ coverage.** Missing = warehouse inventory. Coverage = selected picks.
6. **Either/or is one requirement** for both missing and coverage.
7. **IMPLIES is warehouse-only.** The JD is not rewritten to ask for SQL just because it asked for PostgreSQL.
8. **Longest span wins.** `C++` is never also `C`; `Node.js` is never also `JavaScript`.
9. **Degree lines and Benefits/EEO/pay are not skills.**
10. **JS-rendered job pages will be thin.** Paste is the supported fallback.
